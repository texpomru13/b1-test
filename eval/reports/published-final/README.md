# Официальные публикации

Стенд приёмки обработал 60 авторских вопросов по зафиксированным русскоязычным PDF и шесть дополнительных запросов на изоляцию документов. Все 66 запросов последовательно прошли через публичный API. Контрольные суммы приложения, вопросов и исходных данных зафиксированы до измерения.

| Показатель | Результат |
|---|---:|
| Валидные HTTP-ответы по схеме | 66 из 66 |
| Положительные вопросы с выданным ответом | 32 из 40 |
| Корректные отказы при отсутствии ответа в документе | 20 из 20 |
| Корректные отказы при подмене документа | 6 из 6 |
| Цитаты с точными координатами, текстом и страницей | 68 из 68 |
| Цитаты из чужого документа | 0 из 68 |
| Полный набор эталонных выдержек попал в контекст | 39 из 40 |
| Задержка HTTP, медиана / 95-й перцентиль / максимум | 22,3 / 38,1 / 193,1 с |

Среди восьми ложных отказов в семи весь эталонный материал попал в переданный контекст. Три раза генератор объявил сведения недостаточными, четыре раза проверка источников отклонила утверждения и один раз их отклонил верификатор. Например, для двух строк ставок по вкладам сервер потребовал разделить числовые значения с разными условиями. Для вопроса о реестре космических объектов одна из нужных выдержек также осталась вне контекста. [События исходных запросов](observed-refusals.json)

При 32 ответах из 40 доля полностью корректных ответов ограничена сверху 80%. Для заданного порога в 85% требуются как минимум 34. Оценка полноты и смысловой точности каждого выданного ответа собрана в [разборе утверждений](REVIEW.md).

В [манифесте](manifest.json) записаны контрольные суммы кода приложения, образов, PDF, индексных экспортов, вопросов и ответов. Договор аренды из демонстрации использован один раз для прогрева после перезапуска. Этот запрос исключён из всех долей и перцентилей. [Запись прогрева](warmup.json)

## Почему ответы не прошли проверку доказательств

Стенд записал стадию, причину и ID запроса. Текст отвергнутого черновика в журнале отсутствует. Чтобы проверить сам валидатор, для четырёх вопросов взяли контекст из записанного ответа API и передали в тот же код правильные утверждения с выданными сервером ID. Это отдельная проверка без обращения к модели. [Исходные события](observed-refusals.json) · [Код контрольной проверки](check_evidence.py)

| Вопрос | Что установлено |
|---|---|
| `bulletin-07` | В одной выдержке есть две ставки для разных сроков и границы «до 1 года» и «свыше 1 года». Корректный ответ «Для срока свыше 1 года значение составляет 15,05%» отклонён с той же причиной, что в журнале. Валидатор объединил условия по числу и единице «1 год», хотя они относятся к разным строкам диапазонов. Отдельное утверждение о 15,15% для 91–180 дней прошло. |
| `nairobi-01` | Вся статья с подпунктами (1)–(4) образовала одну нормативную единицу в 1 673 символа. Даже полный дословный подпункт (4) об исключении для СМИ отклонён с требованием воспроизвести всю статью. Её длина также выше лимита экстрактивного восстановления в 1 600 символов. |
| `echr-05` | Оба правильных утверждения об адресате и публикации проходят на цитатах из пунктов 3 и 4. В двух запросах проверки отклонено число 16, которого в этих пунктах нет. Оно входит в название протокола в вопросе. Для ответа на вопрос повторять его не требуется. |
| `space-02` | В контекст вошёл пункт о ведении реестра Генеральным секретарём. Положения о полном и открытом доступе в переданных выдержках нет. Журнал зафиксировал ошибку структуры черновика и затем неизвестный ID доказательства. Ответить на обе части из доступных выдержек было невозможно. |

Первая проверка локализует дефект в сопоставлении диапазона со ставкой, вторая — в границах нормативного пункта. Для этих случаев можно проверять величину внутри своей строки и выделять пронумерованные подпункты вместе с управляющей фразой. Ограничения суммы, срока, субъекта и исключения при этом должны подтверждаться одними и теми же координатами.

## Пересчёт

Выполните из корня репозитория. Для повторной сверки текста исходных PDF нужны зависимости приложения, Poppler и Tesseract с русским и английским языками. Tesseract может брать языковые данные из установленного системного каталога или из `TESSDATA_PREFIX`.

```sh
repo_root=$PWD
report="$repo_root/eval/reports/published-final"
export B1_EVAL_PACK=published-six
export B1_EVAL_WORK_DIR=$(mktemp -d)
tar -xzf "$report/inputs.tar.gz" -C "$B1_EVAL_WORK_DIR"
mkdir -p "$B1_EVAL_WORK_DIR/runs/final"
cp "$report/manifest.json" "$report/responses.jsonl" "$report/claim-review.json" "$B1_EVAL_WORK_DIR/runs/final/"
uv run --frozen python eval/qualification_data.py --check-index
uv run --frozen python eval/metrics.py --run final
uv run --frozen python "$report/check_evidence.py" "$B1_EVAL_WORK_DIR"
uv run --frozen python eval/qualification_review.py score --run final
```

Для отдельной ручной оценки скопируйте в отдельную рабочую папку снимок индексов, манифест и ответы. Создайте пустой бланк через `qualification_review.py prepare --run final`. Эталон и исходные PDF можно независимо проверить по [листу сверки](../../packs/published-six/source-review.md).
