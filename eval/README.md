# Оценка ответов на корпусе договоров

Для проверки основных операций достаточно `sh eval/demo.sh` на запущенном сервисе. Полная проверка ниже измеряет качество поиска и ответов через публичный API. [Запуск сервиса и примеры](../README.md) · [Протокол проверки по ТЗ](../AUDIT.md)

## Что измеряется

Эталон содержит 133 вопроса к 14 текстовым договорам, из них 93 с ответом и 40 без ответа. Есть 17 дополнительных запросов к чужому документу, всего 150 обращений к API. В историческом прогоне отдельно проверяли индексацию файла на 100 страниц и отказ `OCR_REQUIRED` для скана № 06. В текущей версии скан № 06 также должен успешно пройти индексацию через локальное OCR. Документы разделены на две выборки, 35 вопросов в dev и 98 в holdout. Вопросы подготовили модели, исходные цитаты сверены с текстом автоматически. Часть контрольных примеров использовалась при разборе ошибок. [Вопросы и эталонные выдержки](gold/gold.jsonl) · [Документы корпуса](../test_documents)

- `run_qa.py` сохраняет HTTP-статус, время запроса и весь ответ с диагностикой. Сбои сервиса и ошибки формата учитываются при расчёте доли успешных запросов.
- `metrics.py` проверяет структуру ответа, документ и координаты каждой цитаты, корректность отказа и наличие эталонных свидетельств на разных этапах. `found_covers_all_gold_spans` показывает, в скольких выданных ответах итоговые цитаты покрыли все эталонные выдержки.
- `judge.py` с отдельной локальной моделью проверяет ожидаемые и запрещённые факты. Число запрещённых фактов охватывает только ошибки, перечисленные в разметке. Для оценки общей смысловой точности нужна проверка специалистом.

Вопрос `03-06` проверяет, вправе ли заказчик перепродавать услуги. Для обоснованного ответа нужны и сам запрет из п. 6.10, и подпункты, перечисляющие действия. [Вопросы и ответы о договорных условиях](reports/submission/governing-clauses.json)

## Повторить полный прогон

Команды выполняются из корня репозитория. Понадобятся Docker с Compose v2 и `uv`. Стенд получит собственные тома и порт, файлы расчёта останутся в отдельном рабочем каталоге. Пример использует локальные модели. Если указать адрес сервиса с облачной моделью, запросы будут тарифицироваться провайдером. Ограничение расходов задаётся у провайдера.

```sh
export B1_EVAL_WORK_DIR="$PWD/eval/work/verification"
API=http://127.0.0.1:8021
B1_PROJECT=b1-eval-check ./run --build --provider ollama --quality balanced --strict-profile --port 8021

uv run --frozen python eval/upload_corpus.py --api "$API"
uv run --frozen python eval/export_index.py --project b1-eval-check --api "$API"
uv run --frozen python eval/build_gold.py
uv run --frozen python eval/run_qa.py --api "$API" --project b1-eval-check --run balanced-check
for split in all dev holdout; do
  uv run --frozen python eval/metrics.py --run balanced-check --split "$split"
done
uv run --frozen python eval/report.py --runs balanced-check
```

Загрузка использует сохранённые идентификаторы и возобновляет опрос задач после перерыва. Для другого профиля создайте новый каталог и выберите другое имя прогона. `build_gold.py` сверяет цитаты с экспортированным текстом и записывает актуальные координаты в `$B1_EVAL_WORK_DIR/gold.jsonl`. При отсутствии этого файла скрипты используют эталон из репозитория. Сырые ответы и метрики находятся в `runs/balanced-check/` внутри рабочего каталога, сводка — в `REPORT.md`.

### Дополнительные измерения

Для оценки полноты ответов нужен запущенный на хосте Ollama с отдельной моделью-судьёй. В тестовом стенде используется `qwen3.6:27b-q4_K_M`. Команда ниже считает ожидаемые и запрещённые факты. Без `--skip-ragas` рассчитываются также метрики RAGAS.

```sh
uv run --frozen --project eval python eval/judge.py --run balanced-check --skip-ragas
uv run --frozen python eval/report.py --runs balanced-check
```

Пока стенд работает, `uv run --frozen python eval/ablation.py --project b1-eval-check --name balanced` сравнивает dense, BM25, RRF, DBSF и RRF с реранкером на тех же фрагментах.

После проверки остановите только этот стенд.

```sh
B1_PROJECT=b1-eval-check ./run stop
```

## Три набора по реальным документам

Каждый набор содержит шесть документов и 60 вопросов. Ещё по одному вопросу о конкретном объекте каждого документа задаётся к чужому документу. Цель — оценить полноту ответа, точность условий и лишние утверждения. Метрики рассчитываются отдельно для каждого набора. Старые договоры уже участвовали в разработке. Две новые группы содержат опубликованные источниками PDF. Ссылки на первоисточники и датированные копии позволяют проверить, какая редакция легла в основу вопроса.

| Набор | `B1_EVAL_PACK` | Лист для независимой проверки |
|---|---|---|
| Новые вопросы по исходным договорам | `original-six` | [Вопросы и страницы PDF](packs/original-six/source-review.md) |
| Опубликованные документы и международные соглашения | `published-six` | [Вопросы и страницы PDF](packs/published-six/source-review.md) |
| Российские оферты, договоры и правила услуг | `external-six` | [Вопросы и страницы PDF](packs/external-six/source-review.md) · [Издатели и источники](packs/external-six/SOURCES.md) |

Дополнительно можно выбрать `qualification` — 60 вопросов по шести новым синтетическим документам. Они проверяют таблицы с близкими суммами и правила с несколькими условиями. Эти примеры учитываются отдельно от 180 вопросов по реальным PDF. [Лист сверки синтетического набора](qualification/source-review.md)

В каждом листе есть область действия вопроса, необходимые сведения и условия, необязательные подробности и выдержки по каждому факту. Индексы доказательств в `span_ids` начинаются с единицы. `qualification_data.py` сверяет хеши, извлекает текст исходных PDF тем же парсером, что и приложение, и проверяет координаты всех выдержек. Для каждого независимого замера зафиксируйте код и модели до первого запроса. После настройки по результатам используйте этот набор для регрессий.

Для проверки исходных PDF с изображениями на хосте нужны `pdftoppm`, Tesseract и языковые данные `rus` и `eng`. В Ubuntu/Debian установите `sudo apt-get install poppler-utils tesseract-ocr tesseract-ocr-rus tesseract-ocr-eng`, в macOS с Homebrew — `brew install poppler tesseract tesseract-lang`. Команда `tesseract --list-langs` должна вывести оба языка. Если бинарные программы уже установлены, можно взять языковые данные из собранного контейнера worker.

```sh
export TESSDATA_PREFIX="$PWD/eval/work/tessdata"
mkdir -p "$TESSDATA_PREFIX"
WORKER=b1-eval-check-worker-1
for lang in rus eng; do
  lang_path=$(docker exec "$WORKER" find /usr/share/tesseract-ocr -name "$lang.traineddata")
  docker cp "$WORKER:$lang_path" "$TESSDATA_PREFIX/$lang.traineddata"
done
tesseract --list-langs
```

После выгрузки индекса `--check-index` сверяет эталон с тем текстом, который видит QA в запущенной сборке. При расхождении используйте тот же стек OCR и извлечения, что и при фиксации набора.

Укажите адрес уже запущенного API и имя запущенного проекта Compose. Выберите строку из таблицы. Отдельная переменная рабочего каталога сохраняет результаты каждого набора.

```sh
export B1_EVAL_PACK=external-six
export B1_EVAL_WORK_DIR="$PWD/eval/work/acceptance-$B1_EVAL_PACK"
API=http://127.0.0.1:8021
PROJECT=b1-eval-check
uv run --frozen python eval/qualification_data.py
uv run --frozen python eval/upload_corpus.py --qualification --api "$API"
uv run --frozen python eval/export_index.py --api "$API" --project "$PROJECT"
uv run --frozen python eval/qualification_data.py --check-index
uv run --frozen python eval/run_qa.py --api "$API" --project "$PROJECT" --run final
uv run --frozen python eval/metrics.py --run final
uv run --frozen python eval/qualification_review.py prepare --run final
```

Для наборов в `eval/packs/` команда `uv run --frozen python eval/compile_pack.py "$B1_EVAL_PACK"` сверяет эталон с черновиками и PDF. Команда сохраняет уже заполненный лист. Если нужна отдельная копия листа с работающими ссылками для другого каталога, выполните `uv run --frozen python eval/qualification_data.py --source-sheet "$B1_EVAL_WORK_DIR/source-review.md"`.

### Проверка содержания и порогов

1. До знакомства с ответами проверьте PDF по листу для выбранного набора. Отметьте согласованные вопросы, укажите имя. Оставьте комментарии к спорным фактам или отрицательным вопросам.
2. Для проверки ответов откройте `runs/final/review-input.json` и заполните `runs/final/claim-review.json` в рабочем каталоге. В поле `reviewer` укажите имя, в `reviewer_type` — `human`. Для каждого необходимого факта и условия отметьте `required_covered`. Для каждого отрывка ответа оцените **все** его утверждения по цитатам, области действия и вопросу. Даже одного искажения достаточно для отрицательного вердикта по отрывку. Для ошибки укажите `reason` и признак `critical`. Возможны `supported`, `unsupported`, `wrong_scope`, `contradiction`, `irrelevant`. Примеры в `known_errors` дополняют открытую проверку. Нумерация, текст отрывков и отпечатки входных данных фиксированы.
3. Для отдельной оценки моделью вместо ручной разметки ответов запустите `uv run --frozen python eval/qualification_review.py model --run final` после замеров задержки. Используется отдельная локальная модель Ollama. Каждый сохранённый вердикт привязан к входному тексту. При сравнении разных проверяющих используйте копии каталога прогона.
4. Выполните `uv run --frozen python eval/qualification_review.py score --run final --source-review ПУТЬ_К_ЛИСТУ.md`. Доли и пройденные пороги появятся в `runs/final/qualification.json`. В поле `reviewer_type` останется фактический тип проверяющего. Статус независимой человеческой приёмки требует заполненного листа источников и оценки ответов человеком.

Пороги для каждого полного прогона — 90% обязательных фактов с условиями, 85% полных корректных ответов среди положительных вопросов, ноль критических искажений, все предусмотренные отказы и проверки изоляции, 100% валидных ответов и точных координат цитат. Выданный ответ с ошибочным добавлением не засчитывается как полный, даже если все нужные факты присутствуют. Отказ или техническая ошибка на положительном вопросе дают нулевое покрытие его фактов. После изменения сырых ответов, метрик или текущих входов необходимо повторить проверку согласованности.
