# Проверка по тестовому заданию v2.1

Критерии взяты из разделов «Бизнес-задача», «Состав API», «Технические требования» и «Результат выполнения». Уточнение заказчика допускает LangGraph. Для трёх операций, перечисленных в исходном тексте, проверяется фактическое использование LangChain.

## План проверки и исправлений

| Этап | Что проверяем | Критерий приёмки |
|---|---|---|
| 1. Запуск | Чистая конфигурация, выбор моделей, переменные окружения, готовность зависимостей, повторный запуск | По инструкции запускается работающий API. Параметры действительно достигают сервисов |
| 2. Индексация | Загрузка PDF и DOCX, задача Celery, Redis, лимиты, повторная доставка, сбои | Загрузка возвращает 202 до завершения индексации. Документ на 100 страниц проходит, 101 страница даёт объяснимую ошибку. Частичный индекс недоступен для вопросов |
| 3. Хранилище и поиск | Схема коллекции, индексы payload, фильтры, обе ветви и их объединение, отдельный реранкер | Каждая точка содержит текст, координаты и два вектора. Вопрос видит только опубликованные фрагменты выбранного документа. Верхние фрагменты отбираются после переранжирования |
| 4. Ответ и диагностика | Точное обозначение, перефразирование, отсутствующий факт, вопрос к чужому документу, отсутствие памяти | Ответ валиден по Pydantic. Цитата совпадает с текстом и страницей. При отсутствии сведений возвращаются `found=false` и пустой список цитат. Сбой зависимости виден клиенту |
| 5. Результаты и документация | Исторические метрики и ошибочные ответы, воспроизводимость демо, README, OpenAPI | Проверяющий может воспроизвести примеры, увидеть границы качества, понять архитектуру и объём работ перед production |
| 6. Регрессия | Линтер, типы, модульные тесты, интеграционные проверки и запросы через публичный API | Есть результаты запуска на исправленном коде и явные границы проверки |

Все четыре требуемые операции доступны через FastAPI. Celery выполняет индексацию в фоне, Redis хранит состояние задачи, Qdrant хранит фрагменты всех документов в одной коллекции. У каждой точки есть плотный вектор, вектор BM25 и перечисленные в ТЗ поля payload. К списку кандидатов приводит один запрос Qdrant с двумя ветвями и настраиваемым объединением. Отдельный реранкер оценивает кандидатов до передачи контекста модели. При `debug=true` дополнительный диагностический запрос измеряет размер каждой ветви. Ответ проходит валидацию Pydantic, обработчик вопросов не использует историю диалога. [Контракты и конфигурация](README.md) · [Поиск и фильтры](app/retrieval/search.py) · [Интеграционные проверки](tests/integration)

## Что обнаружено и исправлено

| Область | Исходное расхождение | Исправление и способ проверки |
|---|---|---|
| LangChain | Для разбиения уже использовался LangChain, для LLM — его чат-модели. Энкодер напрямую вызывал SentenceTransformer | Добавлен адаптер `Embeddings` с `embed_documents` и `embed_query`. На реальных весах Giga-480M обе реализации дали побитово одинаковые результаты для двух текстов и вопроса. Оркестрация вопроса сведена к функции с ограниченным циклом генерации и проверки, прямая зависимость от LangGraph удалена |
| Координаты и метаданные | Одинаковый текст мог ссылаться на предыдущее вхождение. Длинная фраза подпункта попадала в название раздела. При загрузке без `title` имя документа терялось | Разбиение отслеживает исходные позиции, раздел получает заголовок либо номер пункта, заголовок документа по умолчанию берётся из имени файла. Проверены повторяющиеся страницы, короткий PDF и инварианты цитат на корпусе |
| Изоляция и восстановление индекса | После прерывания создания коллекции часть payload-индексов могла отсутствовать. При смене энкодера поиск мог обращаться к старым векторам | При повторном старте достраиваются недостающие индексы. Перед поиском сверяется отпечаток индекса. Воркер проверяет принадлежность попытки при записи прогресса и постоянство параметров модели между батчами. Интеграционные тесты проверяют частичную запись, повторную доставку и восстановление после падения |
| Обоснованность ответа | В случае `10-09` модель подтвердила ссылку на порядок определения расходов как ответ на вопрос о конкретном проценте | Генератор и проверяющий учитывают запрошенную величину и полноту. Для прямого вопроса о числе добавлена проверка случая, когда ответ целиком сводится к отсылке. Есть тесты для процентов прописью, долей, нуля и вопросов да/нет. Смысловая проверка модели остаётся вероятностной |
| Обработка вопроса | При холодном старте параллельные вопросы обходили ограничение. При неполном ответе реранкера часть кандидатов могла остаться без оценки. Текстовые блоки OpenAI могли не разобрать как JSON | Исправлены синхронизация при инициализации, проверка полного набора оценок, учёт повторных вызовов модели, извлечение текста и различение ошибок формата, недоступности и отсутствия доказательств |
| Конфигурация и готовность | Тяжёлый профиль выбирался по умолчанию, проверка готовности пропускала LLM. Часть флагов и параметров подключения не действовала | По умолчанию выбран измеренный профиль `balanced`. Учитывается память для одновременно загруженных моделей. Исправлены сохранение настроек, работа с путями и проверка аргументов. LLM проверяется через метаданные без генерации. BM25 загружается до готовности API. Ключ и таймаут Qdrant, а также длительность индексации передаются в соответствующие процессы |
| Публичный контракт | Реальные ответы об ошибках отличались от OpenAPI. Обрыв Redis на чтении мог вернуть 500. Несколько описанных в README ограничений уже устарели, в частности `section: null` уже сохранялся в JSON | OpenAPI описывает общий конверт для ошибок маршрутов и PDF для скачивания. При временной потере реестра API отвечает 503, для повторяемых 429/503 передаёт `Retry-After`. Обновлены инструкция и примеры |
| Проверка результатов | Демо могло закончиться с кодом 0 после проваленной индексации, ошибки HTTP или неверного ответа. Экспорт корпуса зависел от первых ста документов и текста заголовка | Демо проверяет HTTP, задачу, сумму, отказы и связь между контекстом и цитатами. Экспорт берёт точные ID из записи загрузки. Рабочий каталог нового прогона отделён от исторических результатов |

## Полученные ранее результаты

Для `balanced-9b-t0` детерминированные метрики пересчитаны из 150 сохранённых ответов, канонических текстов и опубликованных чанков. Итоги по всем случаям, dev и holdout совпали с сохранёнными значениями. Эталон содержит 133 вопроса по 14 документам, дополнительно выполнено 17 проб изоляции.

| Критерий | Исторический результат | Что это означает для ТЗ |
|---|---|---|
| Ответ при наличии сведений | 79/93 | В 14 случаях сервис отказал, хотя эталон содержит ответ |
| Отказ при отсутствии сведений | 39/40 | В одном случае выданы подлинные цитаты, которые не содержат запрошенный процент |
| Изоляция документов | 17/17 правильных отказов | Во всех этих пробах документы разделены |
| Полнота по локальному судье | 45/93 полностью отвеченных вопросов, 171/248 ожидаемых фактов | Наличие корректной цитаты ещё не гарантирует полного ответа |
| Источник среди кандидатов | 93/93 вопроса с ответом | Для всех вопросов этой выборки источник доступен до формирования ответа |

Разбор 14 пропусков показал, где искать причину. Во всех 14 случаях эталонное свидетельство было среди кандидатов. Для трёх вопросов оно выпало из контекста после ранжирования. Например, условие об оплате банковским переводом для `13-03` заняло десятое место при лимите восемь. Для остальных 11 все эталонные фрагменты попали в контекст. В `01-02` реквизиты стороны были в первом фрагменте на странице 8, но модель вернула отказ. Архив этого прогона не позволяет установить, на каком шаге обработки ответа возник каждый из этих 11 отказов.

Изменённые числовые проверки дополнительно применены к 80 положительным ответам старого прогона. Они отклонили только `10-09`. Это проверка сохранённых ответов, качество генерации после изменения промпта измеряется отдельно. [Архив ответов и метрик](eval/reports/runs/balanced-9b-t0)

### Запрет в перечне подпунктов

В договоре VDS вопрос `03-06` проверяет, вправе ли заказчик перепродавать услуги. Заголовок п. 6.10 содержит запрет. Подпункты 6.10.2 и 6.10.4 перечисляют действия. В исходном прогоне `found=true` скрывал фактическую ошибку. Модель ответила «вправе». Судья не засчитал ни один из двух ожидаемых фактов. Исправленный сервис отказал, что сохраняет ограничение по доказательствам, однако оставляет вопрос без ответа.

Отдельно проверено объединение короткого перечня с управляющей фразой. На этом договоре весь список поместился в 205 токенов и занял первое место после реранжирования. Верификатор всё равно дважды отклонил утверждения и модель вернула отказ. На корпусе такое разбиение изменило бы границы у 10 из 14 документов. Изменение оставлено в эксперименте. Для дальнейшей работы с такими вопросами следует размечать обе части доказательства — запрет и подпункт — и проверять попадание обеих в цитаты на независимой выборке.

## Совместимость и границы

- Проверены все 14 опубликованных документов из старого локального индекса. Для 2 011 чанков текст по сохранённым координатам совпадает с каноническим текстом. Исходный профиль воспроизводит прежний отпечаток. Для применения улучшенных меток и координат к старому файлу можно отправить его с новым `Idempotency-Key`.
- Доступность ранее опубликованного документа зависит от Redis, Qdrant и файлового тома. Redis содержит состояние задач и идентификатор опубликованной попытки. Согласованное резервное копирование этих данных входит в подготовку к production.
- Тесты провайдеров проверяют разбор ответа и классификацию ошибок на их контрактах. Живой прогон выполнен на macOS с локальным Ollama. Холодная установка без кэша весов, Windows/WSL2, NVIDIA, DMR и платные провайдеры требуют отдельных стендовых проверок.

## Проверка исправленного сервиса

Основной стенд работал на macOS Apple Silicon, Docker Compose, Ollama и профиле `balanced`. Для него были созданы отдельные тома Redis, Qdrant и документов. Веса моделей уже были доступны локально. После проверки стенд остановлен с сохранением данных. На этой машине его можно снова запустить из корня проекта командой `B1_PROJECT=b1-verify1120 ./run` и обратиться к API на порту 8020.

- Живой запрос `10-09` к страховому договору вернул HTTP 200, `found=false` и пустые цитаты. Для этого запроса обе ветви нашли по 60 фрагментов, реранкер оценил 60 кандидатов и передал в контекст 8. [Ответ и диагностика](eval/reports/acceptance/2026-11-20/regression-10-09.json)
- В отдельных экземплярах FastAPI из рабочего образа поочерёдно указывался недоступный адрес Qdrant или Ollama. В обоих опытах `/health/ready` определил недоступную зависимость, а вопрос к опубликованному документу вернул `503 DEPENDENCY_UNAVAILABLE`, `retryable=true` и `Retry-After: 5`.
- Прошли 24 интеграционные проверки индексирования, поиска, токенизатора, Redis и восстановления состояния. Для них использовались реальные Redis, Qdrant, энкодер и реранкеры. Отдельные 9 тестов через публичный API проверили запуск, загрузку и опрос задачи, DOCX, неверные PDF, ограничение числа страниц, вопрос по номеру пункта, отсутствие сведений и независимость вопросов.
- 14 текстовых договоров из корпуса проиндексированы. Для скана № 06 задача вернула `OCR_REQUIRED`. Дополнительный PDF на 100 страниц был принят за 19 мс, индекс содержит 896 фрагментов. От отправки до публикации прошло 552.7 с, включая очередь остальных файлов. С момента первого наблюдения фоновой обработки — около 205 с. [Журнал индексации корпуса](eval/reports/acceptance/2026-11-20/indexing.json)
- Демо по двум договорам прошло все проверки. Ответ с точной суммой привязан к п. 3.1.1 на странице 5, перефразированный вопрос по сроку аренды дал 11 месяцев от подписания передаточного акта. Подтверждены отказ по отсутствующему условию, отказ по чужому договору и идентификаторы использованных цитат в диагностике. [Полные ответы демо](eval/reports/acceptance/2026-11-20/demo)
- На финальной сборке прошли все 229 тестов без пропусков: 196 модульных и 33 интеграционных. Команда для стенда — `RUN_STACK_TESTS=1 B1_TEST_API_URL=http://127.0.0.1:8020 uv run --frozen pytest -q -ra`. Ruff прошёл, mypy проверил 61 исходный файл без ошибок. Проверены все три файла фиксации зависимостей — для приложения, локальных моделей и оценки.

## Сравнение качества после исправлений

Во всех трёх столбцах одни и те же 133 вопроса и 17 проб изоляции. Веса моделей и профиль совпадают. После полного повторного запуска добавлена последняя проверка количества предметов. Она работает над готовым ответом и его цитатами, поэтому к каждому из 150 сохранённых ответов применена та же функция, что вызывается в HTTP-маршруте. Изменился один ответ. Его повторно запросили через API.

| Показатель | Исходный прогон | Полный повторный прогон через API | После проверки количества |
|---|---:|---:|---:|
| Структурно валидные ответы | 150/150 | 150/150 | 150/150 |
| Получен ответ на вопрос с эталонным ответом | 79/93 | 80/93 | 79/93 |
| Правильный отказ при отсутствии сведений | 39/40 | 40/40 | 40/40 |
| Правильный отказ на вопрос к чужому документу | 17/17 | 17/17 | 17/17 |
| Цитата совпала с текстом и страницей | 136/136 | 147/147 | 144/144 |
| Все ожидаемые факты в ответе, по локальному судье | 45/93 | 49/93 | 49/93 |
| Подтверждены ожидаемые факты, по локальному судье | 171/248 | 178/248 | 178/248 |

Для оценки фактов на повторном прогоне использовалась та же локальная модель-судья Qwen 27B. Итог по фактам для изменённого ответа равен нулю в обоих вариантах. RAGAS повторно не рассчитывался. Часть исходных случаев holdout уже просматривалась при разработке, поэтому эти числа характеризуют регрессию на известном наборе.

- Вопросы `07-06` о штрафах и `08-05` о графике оплаты получили ответы вместо отказов. По `03-06` и `11-06` получены отказы. Для `03-06` прежнее разрешение перепродажи противоречило договору.
- В вопросе `14-08` о количестве камер повторный прогон выдал «только одну». Цитаты подтверждали однократное участие и один тестовый период на камеру. Договор позволяет до трёх единиц и содержит отдельное исключение. Финальная проверка отклоняет числовое утверждение, если во всех его цитатах речь идёт о другой величине. Она учитывает только цитаты, прикреплённые к этому утверждению. При повторном запросе исходной формулировки API отказал. Если в вопросе назван п. 3.6, сервис на том же документе находит обе величины — три единицы в общем случае и одну при личной явке представителя.
- На уровне поиска для всех 93 вопросов с ответом в кандидатах было хотя бы одно эталонное свидетельство. Для 90 из 93 в контекст вошли все необходимые фрагменты по порогу покрытия. После последней проверки остаются 14 отказов при наличии ответа. Вывод о качестве по новым документам требует отдельной выборки.

### План работы с оставшимися ошибками качества

1. Для каждого из 14 ложных отказов сопоставить эталонный пункт, контекст после реранжирования и результат проверки утверждений. Если свидетельство выпало, проверять отбор фрагментов. Если оно уже в контексте, проверять генерацию и причины отказа. Контрольные случаи — запрет из п. 6.10 договора VDS и лимит оборудования из п. 3.6.
2. Для 30 выданных ответов, где локальный судья не засчитал все факты, вручную сверить пропущенные условия, суммы и исключения с источником. Это позволит отделить дефекты ответа от расхождений в разметке и оценке судьи.
3. Проверять следующие изменения на новых договорах с независимой разметкой. На текущем наборе повторять сравнение полноты, отказов, изоляции документов и точности цитат. Рост числа ответов оценивать вместе с числом неподтверждённых утверждений.
