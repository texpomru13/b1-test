# Тестовое задание по поиску ответов в документах

FastAPI-сервис принимает PDF или DOCX до 100 страниц и отвечает на вопросы по выбранному документу. Вместе с ответом он возвращает дословные цитаты, страницы и координаты текста. Если подтверждения недостаточно, ответ содержит `found=false` и пустой список цитат. Каждый вопрос независим.

## Запустить и проверить

В корне репозитория выполните две команды. Для первой нужен Docker с Compose v2, для второй — также `curl` и `jq`.

```sh
./run --build
sh eval/demo.sh
```

Команда `./run --build` собирает образы, подготавливает модели и ждёт готовности API. Сервисы продолжают работать в фоне. При первом локальном запуске нужны интернет и место на диске для образов и весов. Ключи API не требуются. На Windows используйте `.\run.ps1 --build` из PowerShell с настроенными WSL2 и интеграцией Docker Desktop. Демо запускается в shell внутри WSL.

На macOS 26.7.3 с Apple M4 Max и 128 ГиБ памяти профиль `balanced` вышел в готовность за **7 минут** с пустыми кэшами моделей и новыми томами. Слои сборки Docker были закэшированы. Загруженные веса и кэши заняли **9,15 ГиБ** сверх образов. После `./run stop` команда `./run --offline` восстановила доступ к обоим загруженным договорам за **15 с**. [Условия и протокол первого запуска](eval/reports/cold-start/README.md)

Команда `sh eval/demo.sh` загружает два договора, ждёт индексации и печатает ответы со страницами. Она также проверяет перефразирование, диагностику и изоляцию документов. Ответы API сохраняются в `eval/reports/demo/<время UTC>/`. [Swagger UI](http://127.0.0.1:8000/docs) · [Схема OpenAPI](http://127.0.0.1:8000/openapi.json)

## Управление сервисом

После первой сборки для обычного запуска достаточно **`./run`**. Это сокращение для `./run up`. Скрипт использует собранные образы, запускает контейнеры и возвращает управление, когда `/health/ready` сообщает о готовности Redis, Qdrant и моделей.

| Команда из корня проекта | Когда использовать |
|---|---|
| `./run --build` | При первом запуске и после изменения кода, зависимостей или Dockerfile. Собирает образы и сразу поднимает сервис. |
| `./run` | При повторном запуске, в том числе после `stop` или `down`. Документы и индекс доступны из томов проекта. |
| `./run doctor --json` | До запуска. Показывает ресурсы машины, выбранный профиль, модели и причины выбора. |
| `./run --dry-run --quality balanced` | Проверяет, как применятся параметры запуска, и печатает итоговые настройки. Сервисы при этом остаются в текущем состоянии. |
| `./run status` | Показывает состояние контейнеров и текущий ответ `/health/ready`. |
| `./run logs` | Выводит последние 200 строк журнала каждого сервиса. |
| `./run stop` | Останавливает контейнеры. |
| `./run down` | Удаляет контейнеры и сеть проекта. Как и при `stop`, именованные тома с файлами, индексом, состоянием задач и кэшем моделей сохраняются. |

API по умолчанию доступен на `127.0.0.1:8000`. Для другого порта выполните `./run --port 8001`, затем `sh eval/demo.sh http://127.0.0.1:8001`. Если образы и все веса уже загружены, `./run --offline` запускает локальный сервис из кэша. PowerShell-обёртка принимает те же аргументы, например `.\run.ps1 status`.

## Профили моделей

Профиль задаёт три модели. Энкодер строит векторы для поиска, реранкер отбирает фрагменты, языковая модель формирует ответ. Таблица показывает штатные сочетания для нового проекта с Ollama.

| Профиль | Энкодер | Реранкер | LLM в Ollama | Когда выбрать |
|---|---|---|---|---|
| `balanced` | Giga-Embeddings 480M | bge-reranker-v2-m3 | `qwen3.5:9b-q4_K_M` | По умолчанию. На этом профиле получены показатели в README. |
| `low-memory` | Giga-Embeddings 480M | bge-reranker-v2-m3 | `qwen3.5:4b-q4_K_M` | Когда для LLM 9B недостаточно памяти. |
| `quality-compact` | Giga-Embeddings 3B | bge-reranker-v2-m3 | `qwen3.6:27b-q4_K_M` | Для запуска LLM 27B с компактным реранкером. |
| `quality` | Giga-Embeddings 3B | Qwen3-Reranker-8B | `qwen3.6:27b-q4_K_M` | Для запуска старших моделей поиска и генерации при достаточном объёме памяти. |

**Выбрать конкретный профиль** можно командой `./run --quality balanced --strict-profile`. Флаг `--strict-profile` останавливает запуск, если для запрошенного профиля недостаточно памяти. Без него скрипт перебирает профили от выбранного вниз по порядку `quality` → `quality-compact` → `balanced` → `low-memory`. Для обычного первого запуска выбор начинается с `balanced`. Фактические модели видны в выводе `./run`.

Энкодер закрепляется за проектом, поскольку от него зависят векторы в индексе. Чтобы попробовать профиль с другим энкодером, запустите отдельный экземпляр, например `B1_PROJECT=b1-quality ./run --quality quality --strict-profile --port 8001`, и загрузите в него документы. Для управления этим экземпляром указывайте то же имя, например `B1_PROJECT=b1-quality ./run stop`. Смена только LLM или реранкера переиндексации не требует.

По умолчанию LLM работает локально. На macOS скрипт может использовать Ollama на хосте, также доступен запуск Ollama в контейнере. Параметры `--provider` и `--model` задают провайдера и модель явно. Для OpenAI или Anthropic нужны имя модели и ключ соответствующего провайдера. В этом режиме поиск и переранжирование остаются локальными, а вопрос и выбранные фрагменты передаются провайдеру.

## Структура маршрутов и JSON-контракты

| Метод и путь | Тело запроса | Успешный ответ |
|---|---|---|
| `POST /api/v1/documents` | `multipart/form-data` с файлом и необязательным названием | `202`, идентификаторы документа и фоновой задачи |
| `GET /api/v1/jobs/{job_id}` | Без тела | `200`, состояние задачи, этап, прогресс и ошибка |
| `GET /api/v1/documents` | Без тела. Параметры строки запроса `limit` и `cursor` | `200`, список документов и курсор следующей страницы |
| `POST /api/v1/documents/{doc_id}/questions` | JSON с полями `question` и необязательным `debug` | `200`, ответ с цитатами или сообщение об отсутствии сведений |

Примеры можно выполнить по порядку в одном терминале из корня репозитория. Команды берут идентификаторы из ответа вашего сервиса. Образцы JSON получены в [демо на двух договорах](eval/reports/cold-start/demo).

### 1. Загрузить документ

Поле `file` обязательно. Сервис принимает PDF и DOCX, по умолчанию до 25 МиБ. В `title` можно передать название длиной до 500 символов. Заголовок `Idempotency-Key` необязателен. При повторе с тем же ключом, файлом, названием и настройками обработки сервис возвращает те же идентификаторы. Повторное использование ключа с другими данными даёт `409`.

```sh
API=http://127.0.0.1:8000
FILE=test_documents/04_Аренда_производственного_помещения.pdf
UPLOAD=$(curl -fsS "$API/api/v1/documents" \
  -F "file=@$FILE;type=application/pdf" \
  --form-string 'title=04_Аренда_производственного_помещения')
printf '%s\n' "$UPLOAD" | jq .
DOC_ID=$(printf '%s\n' "$UPLOAD" | jq -er '.doc_id')
JOB_URL="$API$(printf '%s\n' "$UPLOAD" | jq -er '.status_url')"
```

Ответ `202 Accepted` подтверждает приём файла. Адрес задачи также доступен в заголовке `Location`.

```json
{
  "doc_id": "8008d340934c4307a9f95520e4a6f96a",
  "job_id": "91fe413229364cd4a35d828459a3162e",
  "status": "accepted",
  "status_url": "/api/v1/jobs/91fe413229364cd4a35d828459a3162e",
  "document_url": "/api/v1/documents/8008d340934c4307a9f95520e4a6f96a"
}
```

### 2. Дождаться индексации

Опросите `status_url` и переходите к вопросам после `succeeded`. В начале `progress.total` может быть `null`. При `retry_wait` воркер готовится повторить попытку. При `failed` или `cleanup_pending` причину можно прочитать в `error`. Например, если в документе 101 страница, загрузка возвращает `202`, а воркер выставляет `failed` с кодом `PAGE_LIMIT_EXCEEDED`.

```sh
(
  set -e
  while :; do
    JOB=$(curl -fsS --max-time 30 "$JOB_URL")
    printf '%s\n' "$JOB" | jq .
    STATUS=$(printf '%s\n' "$JOB" | jq -er '.status')
    case "$STATUS" in
      succeeded) exit 0 ;;
      failed|cleanup_pending) exit 1 ;;
    esac
    sleep 2
  done
)
```

Ответ `200 OK` для готового договора с 93 проиндексированными фрагментами.

```json
{
  "job_id": "91fe413229364cd4a35d828459a3162e",
  "doc_id": "8008d340934c4307a9f95520e4a6f96a",
  "status": "succeeded",
  "stage": "publish",
  "attempt": 1,
  "progress": {
    "completed": 93,
    "total": 93,
    "unit": "chunks"
  },
  "created_at": "2026-11-21T10:21:28.484470+00:00",
  "updated_at": "2026-11-21T10:21:47.015490+00:00",
  "error": null
}
```

### 3. Получить список документов

```sh
curl -fsS "$API/api/v1/documents?limit=20" | jq .
```

### 4. Задать вопрос по документу

`question` — обязательная непустая строка длиной до 4 000 символов по умолчанию. История диалога не передаётся. По умолчанию `debug=false`, а в ответе три поля — `answer`, `found` и `citations`.

```sh
QUESTIONS="$API/api/v1/documents/$DOC_ID/questions"
curl -fsS "$QUESTIONS" -H 'Content-Type: application/json' \
  -d '{"question":"Какой размер постоянной части арендной платы установлен п. 3.1.1 договора аренды нежилого помещения и включает ли он НДС?"}' | jq .
```

**Ответ по п. 3.1.1.** Цитаты содержат номер раздела, физическую страницу и смещение в тексте. Размер платы и включение НДС указаны в п. 3.1.1.

```json
{
  "answer": "Сумма постоянной части арендной платы составляет 158 400 рублей 00 копеек ежемесячно. [1][2] В указанную сумму включен НДС в размере ставки, соответствующей действующему законодательству РФ. [1][2]",
  "found": true,
  "citations": [
    {
      "id": 1,
      "text": "3.1. Арендная плата за Помещение состоит из постоянной и переменной части:",
      "page": 5,
      "page_to": 5,
      "section": "3.1",
      "chunk_id": "d998e95b-224a-5d2c-a0bd-b0f7be937be1",
      "char_start": 16169,
      "char_end": 16243
    },
    {
      "id": 2,
      "text": "3.1.1. Сумма постоянной части арендной платы за аренду Помещение составляет:\n- начиная с 01 апреля 2022 г. и далее ежемесячно - 158 400 (Сто пятьдесят восемь тысяч четыреста)\nрублей 00 копеек, в том числе НДС в размере ставки, соответствующей действующему\nзаконодательству РФ;",
      "page": 5,
      "page_to": 5,
      "section": "3.1.1",
      "chunk_id": "e66c0051-1d81-52f1-92e0-ee74e322ac0b",

```

`page` и `page_to` — первая и последняя физические страницы цитаты, начиная с 1. `section` содержит номер или название раздела, если его удалось определить, иначе `null`. `chunk_id` указывает на фрагмент индекса. В каноническом тексте документа `text` занимает диапазон от `char_start` включительно до `char_end` исключительно. Для DOCX номера страниц относятся к PDF после конвертации. Если текст получен с помощью OCR, в цитате указаны распознанные страницы в поле `ocr_pages`.

**Вопрос без ответа в договоре** также возвращает `200 OK`. Если доказательств недостаточно, `found=false` и список цитат пуст.

```sh
curl -fsS "$QUESTIONS" -H 'Content-Type: application/json' \
  -d '{"question":"Какой обеспечительный (гарантийный) платёж вносит арендатор по договору аренды нежилого помещения?"}' | jq .
```

```json
{
  "answer": "В документе не найдено достаточно сведений для ответа на этот вопрос.",
  "found": false,
  "citations": []
}
```

**Диагностика поиска.** Передайте `"debug": true` в теле запроса. Команда выводит из объекта `diagnostics` счётчики и идентификаторы процитированных фрагментов.

```sh
curl -fsS "$QUESTIONS" -H 'Content-Type: application/json' \
  -d '{"question":"Какая неустойка предусмотрена п. 5.1 договора аренды при просрочке уплаты арендных платежей?","debug":true}' |
  jq '.diagnostics | {dense_returned, sparse_returned, fused_returned, reranked_count, context_count, cited_chunk_ids}'
```

```json
{
  "dense_returned": 60,
  "sparse_returned": 60,
  "fused_returned": 60,
  "reranked_count": 60,
  "context_count": 8,
  "cited_chunk_ids": [
    "550c3738-f3cb-5987-a1ee-176779f508dc"
  ]
}
```

Обе ветви вернули по 60 кандидатов. Qdrant объединил выдачу в 60 фрагментов, реранкер оценил все 60, в контекст модели попали 8 (`context_chunk_ids`), в ответе процитирован 1 (`cited_chunk_ids`). Для счётчиков отдельных ветвей сервис выполняет дополнительный диагностический запрос. Если замер недоступен, значения равны `null`, а причина указана в `diagnostic_warnings`. ### Дополнительные маршруты и ошибки

| Метод и путь | Результат |
|---|---|
| `GET /api/v1/documents/{doc_id}` | Карточка документа, включая `ready`, имя и размер файла, число страниц и фрагментов после индексации. Адрес приходит в `document_url` при загрузке. |
| `GET /api/v1/documents/{doc_id}/normalized` | Файл `application/pdf`, по которому можно сверить цитату и страницу. |
| `GET /health/build` | Идентификатор работающего экземпляра API и SHA-256 кода, Dockerfile и зафиксированных зависимостей. Оценщик сверяет их перед прогоном. |
| `GET /health/live` | `200`, если API отвечает. |
| `GET /health/ready` | `200`, если Redis, Qdrant, сервис моделей и LLM готовы. При `503` поле `components` показывает, какая зависимость недоступна. |

В маршрутах `/api/v1` ошибка запроса возвращается в объекте `error`. Неизвестный документ или задача дают `404`, вопрос до готовности индекса — `409`, превышение размера файла — `413`, неподдерживаемый формат — `415`, некорректный JSON запроса — `422`. При временной недоступности зависимости сервис возвращает `503` и заголовок `Retry-After`. Например, при недоступности Redis ответ на вопрос имеет следующий вид.

```json
{
  "error": {
    "code": "DEPENDENCY_UNAVAILABLE",
    "message": "job registry is unavailable",
    "retryable": true,
    "request_id": "1cb505d17d804981b58244114b16b5b3"
  }
}
```

## Как проходит запрос

Схемы компонентов, индексации и ответа на вопрос, а также проверки на каждом этапе описаны в [архитектуре сервиса](ARCHITECTURE.md).

1. **Загрузка.** FastAPI сохраняет файл и регистрирует задачу в Redis. Диспетчер передаёт её в Celery через брокер Redis и восстанавливает незавершённые задачи после сбоя. [Приём файла](app/api/documents.py) · [Фоновые задачи](app/jobs)
2. **Индексация.** Воркер читает текстовый слой PDF. Если у страницы есть изображение, но нет пригодного текстового слоя, он распознаёт её локальным Tesseract на русском и английском. Карточка документа перечисляет распознанные страницы в `ocr_pages`. Для цитаты из скана это же поле указывает страницы, которые стоит сверить с изображением в `/normalized`. Для DOCX он сначала получает постраничный PDF через LibreOffice. LangChain делит текст с перекрытием. Сервис моделей строит плотные векторы через LangChain `Embeddings`, FastEmbed строит разреженные BM25-векторы. Одна точка Qdrant хранит оба вектора и поля `doc_id`, `doc_title`, `chunk_index`, `page_from`, `page_to`, `section`, `text`, `char_start`, `char_end`. Redis открывает индекс для поиска после записи всех фрагментов. [Разбиение](app/ingestion/chunker.py) · [Модели](services/local-models/app_lm/server.py) · [Публикация индекса](app/jobs/indexer.py)
3. **Поиск.** Все документы находятся в одной коллекции. Обе поисковые ветви фильтруются по идентификатору документа `doc_id` и опубликованной попытке индексации `ingestion_run_id`. Для этих полей настроены payload-индексы. Один запрос Qdrant объединяет смысловые совпадения dense с лексическими совпадениями BM25 по номерам пунктов, суммам и терминам. Реранкер оценивает фрагмент с названием акции или приложения и управляющими пунктами. Весь этот текст учитывается в бюджете. Для запроса о конкретной акции сервер проверяет принадлежность сведений к ней. Для сравнения сохраняет обе названные области и общие условия. [Гибридный поиск](app/retrieval/search.py)
4. **Ответ.** Чат-модель выбирает идентификаторы конкретных фрагментов для каждого утверждения. Сервер восстанавливает оригинальный текст и координаты. Для условных правил проверяются субъект, модальность и полнота исключения. Сервер проверяет цитаты, числа и координаты. Отдельный вызов модели проверяет смысловую поддержку утверждений и полноту ответа. Для распознанного нумерованного перечня проверяются и подпункт, и применимая к нему вводная фраза. Pydantic валидирует результат. Временные ошибки LLM и Qdrant обрабатываются с ограниченным числом повторов. [Обработка вопроса](app/qa/workflow.py) · [Схема ответа](app/schemas/qa.py)

## Настройки

Параметры задаются через окружение или `.env`. Отдельный сервис держит веса энкодера и реранкера в памяти и обслуживает и API, и воркер индексации. [Полный пример конфигурации](.env.example)

| Параметр | По умолчанию и назначение |
|---|---|
| `FUSION_METHOD` | `rrf`, также доступен `dbsf` |
| `DENSE_TOP_K`, `SPARSE_TOP_K` | По 60 кандидатов от каждой поисковой ветви |
| `RERANKER_MODEL`, `RERANK_INPUT_K`, `CONTEXT_TOP_K` | Для `balanced` — bge-reranker-v2-m3, до 60 кандидатов на входе и 8 фрагментов в контексте |
| `CHUNK_TOKENS`, `CHUNK_OVERLAP_TOKENS` | 450 токенов на фрагмент, перекрытие 64 токена |
| `REDIS_URL`, `CELERY_BROKER_URL`, `QDRANT_URL`, `LOCAL_MODELS_URL` | Адреса реестра задач, брокера Celery, векторного хранилища и сервиса моделей |
| `LLM_MAX_ATTEMPTS`, `QDRANT_MAX_ATTEMPTS` | До 2 попыток на вызов LLM и до 3 на операцию с Qdrant при временных ошибках |
| `QUALITY_PROFILE`, `EMBEDDING_MODEL`, `LLM_PROVIDER`, `LLM_MODEL` | Профиль запуска и выбор моделей. Облачный провайдер включается явно и требует своего API-ключа |

Например, `DENSE_TOP_K=40 SPARSE_TOP_K=30 RERANK_INPUT_K=50 CONTEXT_TOP_K=3 ./run` меняет глубину поиска и реранжирования. Смена энкодера, параметров BM25 или размера фрагмента может потребовать переиндексации документов.

### Совместимость индекса

При загрузке сервис фиксирует параметры извлечения, разбиения и эмбеддингов в отпечатке индекса. При несовпадении параметров запустите отдельный проект Compose, например `B1_PROJECT=b1-scopes ./run --build --port 8022`, и загрузите документы для индексации с нужными настройками.
